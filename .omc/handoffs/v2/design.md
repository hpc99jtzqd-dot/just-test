## 스스로 묻는 질문과 답

### 1. 하루와 주간을 무엇으로 구분해야 하는가?

**결정:** 하루는 길 안에 들어가 걷는 시점, 주간은 산을 바라보며 한 주의 흔적을 읽는 시점이다. 하루에는 숲 입구→들꽃 공터→밝은 숲길→야영지를, 주간에는 현재 초원→암릉→정상을 사용한다.

**근거:** 첨부 1~3은 눈높이의 길·공기·그늘이 중심이고 첨부 4는 위로 이어지는 능선이 중심이다. 기존 장면의 이름만 바꾸거나 카메라만 낮추면 하루 슬롯과 주간 기록이 계속 뒤섞인다.

### 2. 렌더러를 두 개 만들어야 하는가?

**결정:** WebGL 컨텍스트·캔버스·띠 렌더링·캐릭터 SDF는 하나를 공유한다. `day`와 `week`의 장면 기술자에 지형, 경로, 장소, 카메라, 팔레트, 바운딩 박스를 분리한다. 장면을 활성화할 때 명시적으로 텍스처와 유니폼을 바인딩한다. 장면 전용 셰이더는 필요한 때 컴파일하며 처음부터 양쪽을 모두 렌더하지 않는다.

**근거:** 현재 `groundY`, `NXZ`, `EDGES`, `CAM`, `U`가 전역 하나에 묶여 있다. 두 복제본은 선언 충돌·이중 RAF·상태 불일치 위험이 크다. 공용 수학 함수와 장면 데이터의 분리가 먼저다.

### 3. 구체적인 코드 경계는 무엇인가?

**결정:** 순수한 장면 생성 코드를 `src/map-scenes.js`로 분리하는 안을 채택한다. 공용 수학, 기존 등정 지형 생성, 새 하루 지형 생성을 그 안에 둔다. `map.js`는 활성 장면·렌더러·이동·입력 연결을 담당하고 `week.js`는 주간 표시 모델·목록·점프를 담당한다. 제안 인터페이스는 `MAP_VIEW.showDay()`, `showWeek(viewModel)`, `updateWeek(viewModel)`이다. 기존 `WEEK.show/hide/playJump` 외부 계약은 유지한다.

**근거:** `build.py`는 파일을 한 script로 합치므로 새 모듈을 넣으면 `scroll.js → map-scenes.js → map.js → week.js` 순서를 명시해야 한다. `map.js` 초기화 중 아직 선언되지 않은 WEEK를 호출하지 않는다. JOURNEY 규칙·DB 모듈은 분리 작업 대상이 아니다.

### 4. 기존 9개 큰길 슬롯을 월~토 6구간으로 어떻게 바꿀까?

**결정:** 기존 ROAD 전체를 재사용하고 누적 거리의 0, 1/6, …, 1 지점으로 7개 경계를 만든다. 구간 안쪽에 월~토 표지를 놓고 마지막 경계에 일요일 정상 표지를 둔다. 곡선의 샘플과 기존 지형 보정용 앵커는 유지해 산 형태를 보존한다. 하루 슬롯의 이름·원판은 주간에 표시하지 않는다.

**근거:** 현재 큰길은 출발부터 최고점 35까지 연속 상승한다. 단순히 월~토를 기존 슬롯 여섯 개에 꽂으면 토요일과 정상 사이가 과도하게 길어진다. 기존 기하 앵커는 내부 지형 자료이며 화면의 날짜 노드와 분리할 수 있다.

### 5. 주간의 매일 갈림길은 실제 18개 분기여야 하는가?

**결정:** 기본안은 6개 구간 각각의 중심 경로를 해당 날짜의 선으로 표현한다. 1선은 넓은 밝은 자갈, 2선은 풀·들꽃 테두리, 3선은 좁은 흙길과 짧은 점선 표식이다. 각 구간에 `1/2/3선` 글자를 함께 둔다. 이는 이미 선택된 경로의 기록이다. 세 후보가 동시에 열려 있다고 오해시키는 18개 주행 도로는 만들지 않는다. 하루 장면에서는 실제 분기와 합류가 보인다.

**근거:** 현 `week.js`도 6개 선분의 굵기·색으로 선택된 선을 기록한다. 요구의 주간 정보 의미를 그대로 공간에 옮기면서 기존 상승 경로·성능을 지킬 수 있다. 화면 검토 시 분기 의미가 부족하면 표지에 세 갈래 기호와 선택선 강조를 보강한다.

### 6. 주간에 그날 상태를 어떻게 한눈에 보이게 할까?

**결정:** 경로 텍스처에 구간 인덱스를 미리 저장하고 6개 고정 상태 값으로 경로 재질을 고른다. 현재 `uPath` B/A에는 발자국이 있으므로 이를 덮어쓰지 않는다. 주간 전용 RGBA8 보조 텍스처 한 장을 필요할 때 생성하는 안으로 예산을 잡는다. 모자·파손 아이콘·날짜 라벨은 세계 좌표를 투영한 DOM/SVG로 보여 준다. 색만으로 구분하지 않는다.

**근거:** 현재 전역 `uPathOn` 두 값만으로는 날짜별 다른 선을 표현할 수 없다. 여러 떨어진 모자를 전부 SDF 광선 검사에 넣는 것보다 기존 SVG 자산을 쓰는 편이 비용이 낮다. 이 보조 텍스처의 크기와 GPU 메모리도 측정 기록에 포함한다.

### 7. pending, future, before, inferred는 같은 회색으로 처리해도 될까?

**결정:** 다음 표시 모델로 구분한다. `data-state`는 제안한 새 표시 계약이며 DB 필드가 아니다.

| 상태 | 근거 | 화면·DOM |
|---|---|---|
| 기록 있음 | line 1~3, inferred=false | 선택 경로, `data-line`, 장비 흔적 |
| 추론된 빈 과거 | inferred=true | `기록 없음 · 3선`, `data-line=3`, `.wk-empty.wk-none` |
| 오늘 미입력 | key=today, line=null | `오늘 · 미입력`, `.wk-empty`, data-state=pending, 선 번호 없음 |
| 미래 | future=true | `아직`, `.wk-future`, 점선, 선 번호·손실 없음 |
| 기록 시작 전 | 확인된 since보다 앞, 기록 없음 | `기록 시작 전`, data-state=before, 손실 없음 |
| 확인할 수 없음 | 과거 null이며 since/온라인 확인 불가 | `기록 확인 불가`, data-state=unknown, 손실 추정 안 함 |

**근거:** `week()`는 `before` 필드를 제공하지 않는다. 표시 어댑터가 기존 로컬 캐시 `oi.journey.since`를 읽더라도 JOURNEY.ready 뒤 확인된 온라인 정보와 일치할 때만 before를 붙인다. 확인 불가이면 unknown으로 둔다. since에 대한 또 다른 DB 쓰기나 독립 DB 조회는 추가하지 않는다. 캐시 키·값 형태는 구현 첫 단계에서 재확인한다. `line=null` 전부를 3선으로 바꾸지 않는다.

### 8. 요구된 클래스와 목록은 어디에 남기는가?

**결정:** `#wkDays > li` 월~토 6행을 실제로 읽을 수 있는 주간 기록 목록으로 유지한다. 해당 행 내부에 `.wk-hat`, `.wk-broken` 의미 요소를 붙이며 inferred의 손실 아이콘도 누락하지 않는다. `.wk-empty`는 빈 기록 행, `.wk-pending`은 기존 지난 점프 버튼, `.wk-summit`은 활성 정상 조작부다. `data-line`은 확정/추론된 1~3만 허용하며 null이면 생략한다. 3D용 정상과 fallback 정상은 한쪽만 활성화하고 `wkSummit` ID를 중복시키지 않는다.

**근거:** E9는 화면의 목록 내용과 data-line을 검사한다. 숨겨 둔 시험용 DOM만 남기면 정보 접근성이 퇴보한다. 현재 inferred 분기가 손실 설명을 먼저 생략하는 구조는 공통 상태 렌더러로 해소해야 한다.

### 9. 하루 카메라는 얼마나 낮아야 하는가?

**결정:** 초기 조정값은 소년 키를 H라 할 때 카메라 높이 1.1~1.4H, 뒤쪽 거리 4~6H, 옆 거리 1.5~2H다. 소년은 화면 아래 1/3에 약 12~18% 높이로 보이고 길 소실점은 화면 위 35~45%에 둔다. 수관은 양쪽 프레임으로 쓰되 중앙 길과 하늘 틈을 열어 둔다. 수치는 캡처로 확정한다.

**근거:** 기존 카메라 y=45~64는 지도를 내려다보는 시점이다. 첨부 1~3처럼 흙길의 폭과 나뭇잎 그늘이 앞에서 크게 보이려면 새 지형과 낮은 시점이 필요하다. 소년의 등 트램펄린과 캡 챙이 함께 읽히는 3/4 뒤·옆 구도를 택한다.

### 10. 카메라가 계속 따라가면 부분 재그리기를 지킬 수 있을까?

**결정:** 연속 추적 대신 3개 고정 관찰 구간(숲 입구, 들꽃 공터, 야영으로 가는 숲길)을 사용한다. 같은 구간 걷기 동안 CAM은 고정한다. 다음 구간은 경계 노드에 도착했을 때만 한 번 전체 렌더하고 이어 걷는다. 먼 목적지는 경계들을 통과한다. 빠른 재선택에는 취소 토큰을 사용한다. 전체 렌더를 숨기기 위한 매 프레임 카메라 애니메이션은 넣지 않는다.

**근거:** `dwarfRect()`와 scissor는 배경 픽셀이 고정일 때만 유효하다. 낮은 시점에 하루 전체를 한 화면에 억지로 넣으면 원거리 노드가 겹친다. 장면 전환 횟수와 도착 지연을 별도 성능 항목으로 검증하고, 잦은 경계 이동이 발생하면 구간 시야를 넓힌다.

### 11. 하루의 노드는 어떤 장소가 되는가?

**결정:** `dawn`은 숲 입구 이정표, `morning`은 햇빛 드는 작은 벤치, `lunch`는 들꽃 공터의 평평한 돌, `afternoon`은 풀 깎은 길의 쉼터, `evening`은 나무 사이 귀환 표지, `hobby`는 공터, `closing`은 작은 길목 표지, `camp`는 밝은 야영지로 표현한다. `minimum`은 오솔길의 낮은 표지, `sunday`는 주간 점검으로 이어지는 표지로 남긴다. 장소 이름이 실제 PLANS의 과목·시간을 대체하지 않는다.

**근거:** 하루 슬롯은 요일별로 서로 다른 학습 블록을 담는다. 예를 들어 수업 날 라벨은 `b.short/name`을 계속 사용해야 한다. 텐트가 있다고 화면을 밤으로 어둡게 만들 필요는 없다.

### 12. 먼 노드와 가려진 노드는 어떻게 누르는가?

**결정:** 가까운 장소 2~4개는 세계 좌표 라벨, 나머지는 작고 읽을 수 있는 하루 일정 목록에서 접근한다. 모든 노드 ID는 한 조작부에만 배정하고 `.node[data-id]`의 중복을 피한다. 먼 항목 선택도 동일한 `walkTo`로 연결한다. 화면 밖·카메라 뒤·지형에 가린 라벨은 화면 모서리에 무조건 투영하지 않고 일정 목록으로 배치한다. 최소 터치 영역 44px를 목표로 하고 키보드 포커스를 보존한다.

**근거:** 현재 `project()`는 가림 판정이 없고 원근 분모가 작으면 좌표가 폭주한다. 버튼을 0×0으로 만드는 방식은 기존 함정이다. 모바일에서도 야영·최소 기준선에 항상 접근할 수 있어야 한다.

### 13. 실제 하루 갈림길의 그래프는 무엇인가?

**결정:** 기존 연결 의미를 유지한다. 큰길은 dawn→morning→lunch→afternoon→evening→hobby→closing→camp로 굽이친다. SIDE는 dawn→lunch, SPUR는 dawn→minimum→closing이다. 주간 점검 표지는 야영 근처 짧은 연결로 둔다. 큰길은 밝은 흙·쌍바퀴 흔적, 샛길은 깎인 풀과 들꽃, 오솔길은 좁은 흙과 낮은 풀로 구별한다. 비활성 길도 흐린 흔적으로 보여 분기가 존재함을 알린다.

**근거:** `sideOpen()`은 단순히 2선인지가 아니라 오전 칸이 꺼지는지 검사하고, EDGES는 SIDE 비용을 0.7배로 사용한다. 수업 날 규칙을 풍경의 취향 때문에 바꾸지 않는다. 최소 기준선은 3선에서 두드러지되 다른 공부 장소를 영구 삭제하지 않는다.

### 14. 노드 클릭→걷기→두루마리 계약을 어떻게 해석할까?

**결정:** 현재 동작을 보존한다. 다른 노드 클릭 시 이동·정보 갱신, 도착 후 같은 노드를 다시 누르거나 안내판 진입 버튼으로 두루마리를 연다. 걷기 완료만으로 자동으로 두루마리를 띄우지 않는다. `routeFrom`, 속도 이어받기, 재선택, ESC/닫기 및 원래 조작부로 포커스 복귀를 검증한다.

**근거:** 현 `arrived()`는 일반 노드에서 openScroll을 호출하지 않는다. 요청의 화살표를 이유로 두 번 클릭 계약을 몰래 바꾸면 기존 사용감이 달라진다. 일요일 점프만 별도 경로다.

### 15. 일요일 하루 표지와 주간 정상은 중복되지 않는가?

**결정:** 하루 `sunday`는 점검 정보 표지로 남기고, 오늘이 일요일일 때 그 표지에 도착하면 주간 정상 장면으로 연결해 기존 WEEK.playJump 경로를 실행한다. 주간 정상은 일요일에만 버튼이며 평일에는 설명 표지다. 지난 일요일의 미시청 점프는 기존 pending 버튼으로 별도 재생한다.

**근거:** `sundayToday`, `jumpOnArrive`, `WEEK.playJump(pj)`가 현재 연결점이다. 점프 결과는 JOURNEY에서 읽고, 보기 전환 자체가 `markJumpSeen()`을 호출해서는 안 된다. 재생 중 나가면 `endJump(false)` 의미를 보존한다.

### 16. 주간의 캐릭터는 매일 한 명씩 세워야 할까?

**결정:** 주간에는 현재 위치를 나타내는 소년 한 명만 두고 각 날짜의 잃은 장비는 흔적으로 남긴다. 주간 표지 위치는 현재 날짜 구간 또는 일요일 정상이다. 주간 장비 판정은 오늘 날짜를 기준으로 하며, 하루에서 보고 있던 과거 요일의 상태가 새어 들어오지 않게 별도 읽기 모델을 둔다. 하루의 위치·선택·방향은 왕복 시 복원한다.

**근거:** 현재 `trampMode()`는 선택 날짜를 사용한다. 주간 표시까지 전역 dayIdx에 묶으면 과거 요일을 보다가 주간으로 갔을 때 장비가 잘못 나타난다. 캐릭터 6명을 SDF로 늘릴 이유도 없다.

### 17. 캐릭터와 장비를 얼마나 재사용해야 하는가?

**결정:** `dwarf/lostHat/trLocal`, 재질 20~27과 뉴스보이 캡 SVG 형태는 유지한다. 장면별로 위치·방향·카메라만 바꾼다. 2선은 캡 없음, 3선은 트램펄린 상태가 허용할 때 feet, 상실 뒤는 none, 나머지는 back이다. 3선이라는 이유만으로 모자를 잃게 만들지 않는다. 하루 idleYaw는 길 방향 기준의 옆모습으로 조정하여 정면으로 완전히 돌아서지 않게 한다.

**근거:** 현 `hatLost()`는 line===2이며 E4/E5/E20이 장비 계약을 확인한다. 오래된 CLAUDE 설명을 다시 구현하면 회귀다. 3D·SVG·주간 점프에서 같은 소년 실루엣을 확인한다.

### 18. 드림코어를 무엇으로 만들까?

**결정:** 연한 청록~라일락 하늘, 밝은 솜구름, 노란 연두 햇빛, 크림색 길을 기본으로 한다. 한낮의 달 1개, 멀리 구름 위 흰 문 1개, 주변부 비눗방울 소수만 쓴다. 구름은 기존 하늘 함수·텍스처를 활용한다. 문은 길의 목적지와 혼동되지 않을 만큼 멀리 둔다. 사진의 빛 번짐을 따르되 라벨·소년·길 가장자리에는 선명한 윤곽을 남긴다.

**근거:** 첨부 1의 부드러운 노출, 2의 열린 하늘과 들꽃, 3의 잎 그림자가 각각 다른 역할을 한다. 어두운 안개, 끝없는 복도, 위협적인 빈 공간은 넣지 않는다. 장식이 공부 경로의 상태처럼 보이지 않게 비상호작용으로 처리한다.

### 19. 잎 그림자와 빛 번짐의 비용은 어떻게 낮출까?

**결정:** 하루 전용 수관은 적은 수의 큰 덩어리와 줄기로 만들고, 땅의 잎 그림자는 수관 범위에 한정된 정적 세계 좌표 마스크로 표현한다. 그림자는 검정 대신 차가운 녹색이며 명도 하한을 둔다. bloom은 전체 프레임 후처리 대신 광원 주변의 제한된 부드러운 가산광과 정적 공기 원근으로 시작한다.

**근거:** 기존 지형 230·물체 160·그림자 56 반복의 내부에 잎 수백 개나 다중 bloom 패스를 추가하면 SwiftShader 비용이 커진다. 시간 기반 잎 그림자는 부분 재그리기 경계에 이음매도 만든다. 꽃은 기존 지면 재질 마스크를 우선 사용한다.

### 20. 주간/하루 전환 중 어떤 상태를 정리해야 할까?

**결정:** 전환 시작 시 활성 렌더 세대 토큰 증가→이전 띠 RAF 취소→걷기 위치 저장·RAF 중지→두루마리 정리→장면 바인딩→카메라·투영 갱신→전체 렌더→새 입력 활성화 순서다. 소년 idle과 비활성 장면의 갱신은 쉰다. 돌아오면 저장한 노드/길 위 위치에서 이어갈 수 있게 하되 이전 도착 콜백은 취소한다. 버튼은 연속 클릭에도 마지막 요청이 이긴다.

**근거:** 현재 WEEK.show는 패널을 덮을 뿐 breathe/render를 멈추지 않는다. `layoutAll()`도 걷는 중이면 목적지에 도달한 것으로 처리한다. 장면 분리에서는 보이지 않는 이동·점프 실행을 명시적으로 막아야 한다.

### 21. 주간 패널은 3D를 가리지 않는가?

**결정:** WebGL 주간에서는 `.wk`의 불투명 전체 배경을 제거하고 지도 위 날짜 라벨 및 가장자리 기록 영역으로 구성한다. 데스크톱은 머리말과 충돌하지 않는 우측/하단 기록 영역, 모바일은 지도 아래 펼칠 수 있는 6행 목록을 쓴다. fallback일 때만 현재 SVG 배치·배경을 사용한다. `body.wk-on`의 숨김 규칙을 하루 오버레이에 한정한다.

**근거:** 현 `.wk`는 absolute inset:0, z-index:6이며 배경이 불투명하다. 캔버스만 주간으로 바꾸면 실제 사용자는 3D를 못 본다. 헤더의 z-index 7, 점프 9와 터치 영역도 함께 확인해야 한다.

### 22. 무엇을 부분 렌더하고 언제 전체 렌더할까?

**결정:** 캐릭터 이동·장비 변경은 이전/새 캐릭터와 그림자 사각형, 날짜 라벨 변경은 DOM만 갱신한다. 같은 카메라에서 주간 한 구간 재질이 바뀌면 그 구간 폭·원근을 포함한 사각형만 다시 그린다. 장면·카메라·해상도·전체 팔레트 변경 때만 전체 렌더한다. 오래된 `DW.drawn`은 장면 전환 시 폐기한다. 광원·정적 노이즈는 프레임 간 고정한다.

**근거:** `preserveDrawingBuffer`와 기존 `drawRect`를 유지하는 것이 비용 절감의 핵심이다. 낮은 카메라에서는 그림자가 길어지고 근평면을 가로지를 수 있으므로 rect 계산에 깊이 검사·클리핑이 필요하다. 부분 결과와 같은 상태의 전체 결과를 이미지 차이로 비교한다.

### 23. WebGL 없음·컴파일 실패 때 어떤 화면을 보일까?

**결정:** 주간은 기존 `wkSvg`와 동일 목록으로 즉시 대체한다. 하루는 같은 새 경로 데이터의 SVG 길·장소와 기존 소년 SVG를 사용하며 이동·두루마리·장비는 동일하게 작동한다. 하루 fallback 카메라는 읽기 쉬운 별도 투영을 허용한다. context loss도 비활성화/전환 세대 처리를 거쳐 fallback으로 보낸다. 주간 셰이더 실패 시 하루의 잘못된 배경을 주간인 것처럼 남기지 않는다.

**근거:** 현재 initGL 실패는 `.stage.nogl`로 가고 프로그램 교체 실패는 이전 프로그램을 유지한다. 서로 다른 장면으로 확장하면 이전 프로그램 유지가 오히려 오표시가 될 수 있다. 기록·pending은 시각 실패와 무관하게 유지해야 한다.

### 24. 움직임 줄이기는 어떤 결과를 보장할까?

**결정:** 걷기는 즉시 목적지 배치, 카메라 구간 전환은 정지 화면 교체, 숨쉬기·feet 통통·깃발·비눗방울 이동을 중지한다. 점프는 advance/stay/ending 결과와 닫기 버튼을 정적으로 보여 준다. 매체 설정이 실행 중 바뀌어도 반영하도록 이벤트를 연결한다.

**근거:** 현재 reduce는 시작 시 상수이며 CSS와 JS가 나뉜다. 한쪽만 멈추면 접근성 의미가 깨진다. 줄어든 움직임에서도 `markJumpSeen`과 닫기/중단 의미는 같아야 한다.

### 25. 6초 목표를 어떻게 측정해야 믿을 수 있을까?

**결정:** 1280×800, DPR 1, SwiftShader, 고정 서울 시각·fixture·폰트 차단·reduced-motion 조건으로 새 페이지 첫 렌더를 5회 이상 측정한다. 페이지 진입부터 JOURNEY 준비·전체 띠 렌더·`gl.finish()`와 1픽셀 readPixels 완료까지 단조 벽시간을 기록한다. 하루 첫 진입, 최초 주간 전환, 다시 하루 복귀, 하루 구간 전환을 따로 기록한다. 중앙값·최댓값·원시값·브라우저/renderer/해상도를 남긴다. 목표는 각 데스크톱 첫 장면 완료 6초 이하이며 중앙값만 통과하고 이상치가 큰 경우도 보고한다.

**근거:** `__rendered`는 GPU 제출 완료 신호이지 GPU 완료 보장이 아니다. 기존 E2E는 960×720 DPR 0.5라 성능 근거가 될 수 없다. `shots/map-validation.md`의 과거 기록은 1280×800 중앙값 4.694초지만 이번 작업의 재측정값은 아니다. 이번 설계 단계에서는 성능 수치를 새로 측정하지 않았다.

### 26. 성능이 초과하면 무엇부터 줄일까?

**결정:** 첫 화면에서 주간 지형·구름 생성과 셰이더를 지연하고, 비활성 idle을 중지하고, 수관 SDF 수와 겹침·그림자 비용을 먼저 줄인다. 장면별 필요한 물체만 루프에 포함하고 경계 검사로 건너뛴다. 고정 장식 노이즈는 미리 계산한다. 그다음 화면당 픽셀 예산을 측정해 조정한다. 먼저 반복 상한이나 해상도를 무작정 줄여 캡 챙·길을 깨뜨리지는 않는다.

**근거:** 현재 최대 나무 8그루, 바위 4개, DPR cap 1.5, 픽셀 cap 2.3e6, 띠 약 140000픽셀이다. 낮은 시점은 수관·캐릭터가 차지하는 픽셀과 지평선 광선 비용을 늘린다. 기존 예산을 출발점으로 삼고 새 장면에서 다시 측정해야 한다.

### 27. GLSL ES 1.0에서 어떤 새 위험이 생길까?

**결정:** 6개 주간 상태 선택은 상수 상한 루프와 조건으로 처리한다. 동적 uniform 배열 인덱스·GLSL 3 기능을 쓰지 않는다. 텍스처·uniform 한도를 조회하고 추가 보조 텍스처가 가용한지 확인한다. 낮은 카메라를 위해 AABB와 지형 ray 진입/탈출 조건을 장면 속성으로 옮긴다. 색 선형화·톤매핑은 공유한다.

**근거:** 현 main의 y=44/45 및 물체 AABB는 등정 장면 전용이다. 하루 수관이나 뛰는 소년이 상한 밖으로 나가면 잘린다. 루프 제약뿐 아니라 캐릭터 정밀도 `.0004*t`와 재질 분기 순서도 유지해야 한다.

### 28. 시험이 새 구조를 방해한다면 어디를 바꿀까?

**결정:** JOURNEY 시험의 판정 기대값은 유지한다. 지형 시험은 map.js 문자열 경계 추출 대신 순수 장면 생성 코드를 VM으로 로드하게 변경한다. 기존 산의 평탄면·높이 35·상승·최대 경사 2·RG16 정확도·바위 이격 시험을 주간 등정 자산에 그대로 적용하고, 새 날짜 앵커의 오르막 순서도 검사한다. 하루에는 억지로 정상 35/전 구간 오르막을 강제하지 않고 지면 일치·경로 연속·분기 연결·나무 이격·노드 도달 가능성을 검증한다.

**근거:** 현재 `map-terrain.test.cjs`는 `const fract=`부터 `/* 물건들 */`까지 잘라 실행한다. 파일 분리 후 빈 문자열을 테스트하거나 옛 지형만 통과시키지 않도록 실제 생성기를 대상으로 해야 한다.

### 29. E8·E9·E20을 어떻게 확장할까?

**결정:** 기존 assertion을 보존하며 E8에 실제 활성 장면·카메라 변경·하루 위치 복원·빠른 왕복·DB 쓰기 0회를 더한다. E9에 6개 구간의 world anchor/날짜 연결, `.wk-hat/.wk-broken/.wk-empty`, pending/before/future/unknown 구별, 화면에서 보이는 기록을 더한다. E20은 같은 상태 함수를 noGL에서도 재사용하고 SVG 이동·장비·점프를 확인한다. 정상과 pending 재생은 advance/stay/ending, 닫기/중단, 중복 실행을 추가 확인한다.

**근거:** 현재 E8은 패널 표시만 확인하므로 3D 전환이 실패해도 통과할 수 있다. E9는 목록만 확인하므로 캔버스 구간 데이터 연결과 캡처 확인이 별도로 필요하다. 선택자를 새 UI에 맞추는 이유와 대응 의미를 시험 코드에 적고 실패를 숨기는 기대값 완화는 하지 않는다.

### 30. 완성도는 어떤 질문으로 다시 판단할까?

**결정:** 각 캡처에서 “소년 뒤에서 길을 걷는가?”, “길이 굽어 사라지는가?”, “다음 장소가 보이고 먼 장소에도 접근 가능한가?”, “2선과 3선이 색 없이도 구별되는가?”, “주간 월~토가 위로 이어지고 일요일이 정상인가?”, “드림코어가 평온함을 해치지 않는가?”를 확인한다. 하나라도 아니면 장식을 늘리기 전에 카메라·길의 폭·노드 배치를 고친다.

**근거:** 자동 시험은 분위기·구도·정보 과밀을 판단하지 못한다. 사진을 배경으로 붙이는 대신 사진에서 읽힌 공간 관계를 구현해야 한다.

구현 단계 필수 명령:

```text
py build.py
# py가 실패하면 설치되어 실제 실행 가능한 python으로 같은 build.py 실행
node --test tools/journey.test.cjs tools/map-terrain.test.cjs
node tools/journey-e2e.cjs
```

이번 설계에서는 dist가 바뀌는 빌드를 실행하지 않았다. 시험 통과나 새 렌더 시간은 주장하지 않는다. 구현 시에는 빌드 실패 원인·대체 Python 경로를 기록한다. 기존 E2E의 17개 사례가 사라지지 않았는지 이름 단위로 대조하며 추가 사례 수는 별도로 기록한다.

최종 캡처 묶음은 하루 1/2/3선, feet/none, 주간 mixed/pending/future/before, 정상 advance/stay/ending, noGL, reduced-motion을 포함한다. 모든 조합을 중복 캡처하기보다 wide와 phone에 핵심 사례를 분담하고, 자동 검사는 각 상태를 검증한다. 경계 카메라 전환·부분 렌더 차이는 별도 중간 캡처로 work에 둔다.

## 구현 완료 판단

주간은 기존 세체다 방향의 산 자체가 기록판이 되고, 월~토 6구간과 일요일 정상이 실제 화면에서 연결되어야 한다. 하루는 소년 곁의 낮은 시점에서 햇빛·들꽃·나뭇잎 그늘 사이의 길이 멀리 이어져야 한다. 규칙·DB·장비·두루마리·fallback을 보존하고, 전체 시험 및 시각 확인과 GPU 완료 기준 성능 기록까지 있어야 구현 완료로 본다. 이 문서는 그 구현을 위한 결정안이며 구현 결과물은 아니다.
